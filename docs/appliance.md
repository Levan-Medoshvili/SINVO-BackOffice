# Future SimplePOS appliance

Status: architecture decision only. No ISO is generated by the current pipelines.

Keep one Cashier codebase and three delivery forms: Windows x64 installer/portable ZIP, Linux application package, and later a bootable Linux installation ISO. The appliance wraps the same Cashier, synchronization format and device adapters; it is not a fork of the checkout logic. The central server remains a separate role, even if a later small-store installation places both roles on one machine.

The ISO should provide a graphical kiosk session, multi-monitor configuration, network setup, time synchronization, OS credential storage, printer support, a first-boot enrollment wizard and a recovery environment. No company credentials, register identity, private signing keys or customer records belong in the image. Each installation receives a unique identity when enrolled.

Separate OS/application releases from persistent register data. Reinstalling or rolling back the OS must preserve the local database and unsynchronized outbox. Use an explicitly mounted persistent data partition, verified backup/recovery, signed updates, measured free-space checks and an interrupted-update recovery path. A/B OS slots are a candidate, with data-schema compatibility checked before rollback. Do not assume that switching an OS slot reverses a database migration safely.

Pick the appliance distribution after testing the actual TBC/BOG protocols, USB/serial drivers, printer/cutter/cash-drawer support, touch input, GPU and customer display. A general USB port does not make every terminal or printer protocol interchangeable. If a bank provides Windows-only middleware, the Windows Cashier remains a supported deployment option and that device cannot be promised Linux appliance support.

Installation must show the target disk and require an explicit destructive-install confirmation. Include a non-destructive hardware evaluation mode and a way to export diagnostics without exposing credentials or payment data. Remote maintenance must be authenticated and audited; never ship a shared default administrator password.

Build the image only after real hardware and checkout/update recovery tests pass. Jenkins can then produce signed application packages first and feed the tested Linux package into a separate image-building pipeline. The POS itself must not run a CI build agent.
