# SimplePOS 0.5

## Catalog and stock

Products and Categories each have an **Import** button with CSV, Excel and XML examples. Upload a file, review the validation and preview, then confirm. A failed row prevents the entire import. CSV must be UTF-8; both XLS and XLSX are accepted, using the first worksheet. Files are limited to 10 MB and 5,000 data rows. Keep barcode cells as text to preserve leading zeros. Catalog imports do not create stock.

Categories support one subcategory level: Drinks → Alcohol → OLMECA Tequila. Product fields include category, subcategory and Piece / Kilogram / Liter. Existing product units remain immutable because historical and offline sales depend on them. Imports match products by barcode and categories by name plus parent. Category imports can include parents and children in either order. Resolve existing duplicate category names before importing references to them.

Product creation no longer accepts initial branch, warehouse or opening quantity. Existing stock assignments, quantities, price revisions and sale history are preserved. The legacy home-location field remains hidden for migration compatibility. Inventory corrections remain available as audited stock adjustments.

## RS.ge receiving

1. In **Integrations → RS.ge → Settings**, enter the company TIN and RS.ge **service user** credentials, enable, save and test the connection.
2. Open **Waybills**, search a date range and confirmation state or fetch a known waybill ID.
3. Review the source lines, match each product to the catalog, select the receiving branch or warehouse, and confirm units and received quantities. Explain differences and unit conversions.
4. Receive stock. Each posted receipt records its operator, location, source XML/hash, mappings and stock movements. Retail prices do not change.

The adapter uses HTTPS SOAP operations `chek_service_user`, `get_buyer_waybills_ex`, `get_waybill` and `get_waybill_units`. It validates buyer TIN, document identity, activated/completed status, goods IDs and quantities. Source XML preserves unknown fields. Immediately before posting, the document is fetched again and its hash must match the reviewed version. A unique company/waybill identity and transactional locking prevent double receiving. A changed, already-received document needs a reviewed inventory correction. This workflow does not acknowledge, reject, cancel, create or modify an RS.ge document.

Search covers up to 31 days and displays at most 200 results. Narrow the date range if necessary. Specialized medicine/timber and conversion cases require operator mapping and review. Credentials and authorized real documents were not available during implementation: live account acceptance remains an installation check. Protocol references: [RS.ge waybill operations](https://services.rs.ge/WayBillService/WayBillService.asmx), supplied v4.0.4 waybill protocol and the existing [mapping research](rs-ge.md). Invoice issuance and OAuth are separate interfaces, outside this receiving workflow.

## Active Directory

In **Integrations → Active Directory**, configure a domain-controller hostname, LDAPS port (normally 636), base DN and a read-only directory service account. The server certificate must be trusted by the ERP host. A private CA PEM certificate can be entered when the directory uses an internal authority. TLS certificate verification and hostname validation remain enabled. LDAP referrals are disabled and network operations have bounded timeouts.

Use **Add AD user**, search an exact UPN or sAMAccountName, select the result and then assign the user's application, branches, groups and permissions in the existing user editor. Newly provisioned users have no branches or permissions. Sign in using the displayed UPN and the AD password. Local accounts are not linked automatically, and AD users do not receive a local password. The identity uses AD objectGUID, so another account cannot take over access by reusing a name. Disabled users and disabled integrations cannot perform new AD sign-ins. Existing local administrator accounts remain available.

The **Configure company integrations** permission governs credentials/settings. **Manage users** governs AD provisioning and role assignment. **Manage inventory** governs receiving, with branch scope enforced for destination selection. Only configured directory users can sign in; this does not import all domain users or map AD groups automatically. Existing bounded Cashier offline grants still apply during an ERP outage. AD connectivity and live account binding require the customer's domain configuration and were tested with protocol mocks only.

Integration passwords are encrypted at rest using an installation-specific key derived from `SIMPLEPOS_SECRET_KEY`. Preserve that secret with database backups; changing it requires re-entering integration passwords. Passwords are never returned in forms or sent to POS devices.

## Display and POS information

BackOffice's top bar and Cashier Preferences offer **System**, **Light** and **Dark** appearance. BackOffice remembers the choice in that browser. Cashier stores it with the device preferences and applies it to both displays. Receipt printing stays light.

A POS terminal's detail page shows its reported OS, OS version, architecture, CPU/logical cores, RAM and local disk capacity/free space. Cashier v0.5 reports this when polling updates, with device inspection cached for ten minutes. Windows includes fixed local disks when allowed; otherwise the Cashier data volume is reported. This is device-supplied information, with a report timestamp, not remote management or hardware attestation.

## Deployment order

Deploy ERP **Production** first, including migrations and dependencies, then publish Cashier **Production** v0.5.0. Existing sessions may require sign-in again after the authentication-backend change. Before receiving liter products at a branch, update its Cashiers: older clients continue receiving piece/kg catalogs and do not see liter products. Install the publisher-built v0.5 package once on legacy devices that lack automatic updates; later releases can be deployed from BackOffice.

Customer update flow: **Cashier updates → available version → all/selected branches → Deploy update**. Official packages configure update verification automatically, and publisher deployment registers each release in BackOffice. Updates wait for an idle checkout with synchronized sales. See the Cashier repository's `docs/automatic-release-publishing.md` for publisher setup. Customers do not import or manage signing keys.
